# 专项审计：隐私泄露与信息安全（平台回调面）

- 触发：用户要求「除真机测试外，功能开发还有什么遗漏；再审计一次，注意隐私泄露与信息安全」
- 审计对象：`remote/platform.pl`（新增的**网络面**）、`remote/gateway.pl`、凭据与日志的落盘方式
- 结论：**发现 7 处真问题，全部已修并有测试守着**；另有 4 项已接受的风险与 5 项功能遗漏，
  逐条列在下面，不含「大概没事」这种判断
- 提交：`dcedf0c`（安全加固）+ 本文件

## 一、已修的问题（每条都有复现证据）

| # | 问题 | 复现证据 | 修法 |
|---|---|---|---|
| 1 | **重放攻击**：同一份合法请求重发，agent 被跑第二遍 | 探针连发两次同一请求 → 网关被调用 **2 次** | ①时间戳超出 ±300 秒即拒 ②按平台 `MessageId` 去重（TTL 600s），无 ID 时退回签名摘要 |
| 2 | **默认监听 `0.0.0.0`** | `ss -ltn` 显示 `0.0.0.0:<port>` —— 回调正文是明文消息内容，等于向整个局域网公开 | 默认 `127.0.0.1`；要对外须显式 `BIND` 或用穿透/反代 |
| 3 | **请求体无上限** | 3MB 请求体被整块读进内存 | 默认上限 256KB，超限读掉一小段后回 400（直接断连只会让客户端看到「连接重置」） |
| 4 | **并发无上限**（一条消息一个 fork） | 可被刷成 fork 风暴 | 同时处理数上限 8，超出记 `busy_drop` |
| 5 | **凭据/审计/临时文件有 0644 时间窗** | `open` 之后才 `chmod`，umask 022 时存在一瞬间可读 | `sysopen` + `umask(077)`，创建即 0600；测试在 umask 022 下断言仍 0600 |
| 6 | **临时文件残留** | 崩溃后 `~/.claude-agent/tmp` 会一直堆着带消息正文的文件 | 启动清理 1 小时前的陈旧文件（新文件仍是 0600 + 用后即删） |
| 7 | **wide character 崩溃** | 飞书事件含中文时 `sha1_hex` 抛异常 → 整条消息丢失且只留一行 handler_error | 摘要/哈希前统一 `encode('UTF-8', …)` |

写测试时顺带踩到、也一并修掉的两个「看起来像业务 bug」的坑：

- **`SIGCHLD` 打断 `accept()`** → 服务「干净地 exit 0」：第一条消息处理完，子进程退出送信号，
  accept 返回 undef，循环结束。表现为「第二条消息一到服务就没了」。修法：`$!{EINTR}` 重试。
- **服务端输出接 PIPE 而没人读** → 缓冲写满 64KB 后服务端阻塞，后续断言全变成连接失败。
  测试改为把服务端输出落盘。

## 二、隐私相关的核对结果

| 检查项 | 结果 |
|---|---|
| 日志里有没有消息正文 | **没有**：审计只记 `from=<ID> len=<长度>` 与事件名（`inbound` / `gateway_done` / `duplicate_drop`…） |
| 密钥会不会出现在进程命令行（`ps`） | 不会：curl 用 `-K -` 从 stdin 读配置，URL/token 不进 argv；消息内容走 `gateway.pl --stdin` |
| 凭据文件权限 | 0600，创建即 0600（无窗口） |
| 临时文件 | 0600，用后立即 `unlink`，启动清理陈旧文件 |
| 仓库里有没有真凭据 | 0 处：`check-secrets.py --history` 通过（49 个文件 + 全历史） |
| 错误信息会不会回显给平台/攻击者 | 验签失败、去重、忙、陈旧时间戳一律静默（只记审计，不回原因，避免暴露服务存在） |
| 回复会不会发错人 | 只发给「签名验证通过、解密得到的」发送者 ID |
| 白名单 | fail-closed：`ALLOW` 不配就是谁也不许；判定只在 `gateway.pl` 一处 |

## 三、已接受的风险（明确不做，理由写在下面）

1. **本机不做 TLS 终结**：回调地址必须是 https，靠穿透工具（cloudflared 等）或反代终结；
   本服务只监听 127.0.0.1，明文不出本机。要用 `BIND=0.0.0.0` 就必须自己加 TLS。
2. **去重表在内存里**：进程重启后 600s 窗口内的重复消息可能再跑一次。上持久化会引入新故障面
   （写盘、锁），当前场景（个人自用）不值得。
3. **无速率限制**：只有并发上限 8，没有「每分钟最多几条」。白名单是唯一入口，
   白名单外的人连 agent 都碰不到。
4. **审计日志不轮转**：长期跑会一直长。等真出现体积问题再加，现在加等于提前制造坑。

## 四、功能遗漏（开发层面还剩什么）

按影响排序，都**不影响已实现功能可用**，但确实是缺口：

| # | 遗漏 | 影响 | 建议 |
|---|---|---|---|
| 1 | **手机端多轮对话不连续** | platform.pl 每条消息起一个新的 `gateway.pl --stdin` 进程，会话上下文不接续 —— 手机上问「那它的端口呢」接不上上一句 | 改成每个发送者一个常驻网关进程，消息往它的 stdin 里灌（gateway 本来就支持按发送者缓存会话）。**推荐做** |
| 2 | **长回复不截断** | 企微 text 内容上限 2048 字节，超了发不出去（平台返回错误码） | 按平台上限分片发送，或截断并加「…（已截断）」 |
| 3 | **没有「处理中」提示** | 长任务要等十几秒到几分钟，手机上只看到没反应 | 收到消息先回一句「收到，处理中」，完成后发结果。**推荐做** |
| 4 | **NAT 场景缺入队路径** | 档② 的 relay 有队列和轮询端，但**没有客户端往队列里 push**；`platform.pl` 只能直连网关，机器没公网 IP 时走不通 | 给 platform.pl 加 `RELAY_URL/RELAY_TOKEN`，把消息 push 进队列，老 Mac 用 `--poll` 取。**推荐做** |
| 5 | 群聊/非文本消息 | 群 @机器人 的消息不分 `ChatId`；图片/语音/文件直接忽略（记为 `wecom_skip`） | 单聊够用；群聊等有人真要用再说 |

## 五、盲区（明确没验到的）

- **真平台连一次**：回调域名可达性、企微后台的 URL 验证、飞书事件订阅的实际 payload 形态。
  本地验的是「按规范构造的请求能正确处理」，规范细节（如企微某些字段大小写）仍需真环境确认。
- **`openssl` 与 `curl` 的旧版本行为**：本机是 OpenSSL 3.0 / curl 8；macOS 自带的是 LibreSSL，
  `-nopad`、`-K -` 都支持，但没有在真机上跑过。
- **长跑稳定性**：并发上限与去重表在真实流量下的表现没测过（本机没有真实流量）。
- **系统级防护**：防火墙、穿透工具自身的鉴权配置不在本服务职责内。
